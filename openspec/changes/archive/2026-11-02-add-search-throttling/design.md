# Design

## Context

见 `proposal.md - Why`。当前 `HttpSearchTool` 在单次 `search()` 中按顺序调用免费引擎，deep agent 在一次调研中可能多次调用，且失败后没有记忆；同一进程内的多个工作流共享这些外部接口。搜索引擎侧没有可用的配额 API，因此防护必须在进程内完成。

约束：

- 不引入新依赖，保持纯 Python 与现有 `httpx` 调用方式。
- `HttpSearchTool.search()` 的签名、返回的 `SearchResult` 结构与全部失败时的降级契约不变。
- 自定义 `APP_SEARCH_ENDPOINT` 的行为不变。
- 测试环境不能真实等待秒级间隔。

## Goals / Non-Goals

**Goals:**

- 进程内跨 `HttpSearchTool` 实例共享限流、冷却与缓存状态。
- 默认配置开箱即用，且可通过环境变量调整或整体关闭。
- 防护状态与测试可注入时钟，避免测试真实 sleep。

**Non-Goals:**

- 不做跨进程/多实例分布式限流（当前单机单进程部署）。
- 不新增代理池、验证码识别或浏览器自动化。
- 不改变搜索引擎选择策略与解析逻辑。
- 不为自定义 JSON 搜索端点增加限流。

## Decisions

### 1. 独立进程级 `SearchGuard`，而非挂在工具实例上

`ResearchService` 与 deep agent runner 会各自创建 `HttpSearchTool`，实例级状态无法共享。新增 `research/search_guard.py`，以模块级单例保存每个引擎的最后请求时间、冷却截止时间与结果缓存；工具通过构造参数注入，默认为单例。

替代方案：进程级全局变量直接写在 `tools.py`。可工作但难以测试和替换，因此选择带显式接口的 guard 对象。

### 2. 最小间隔用“预留时间片”，不在锁内 sleep

`acquire(engine)` 在锁内计算需要等待的秒数，并把该引擎的下次可用时间推进到 `now + wait + interval`，然后在锁外 `time.sleep(wait)`。这样并发调用者会依次排队，而不会互相阻塞在锁上。

替代方案：令牌桶/滑动窗口。对于“不要频繁调用”的目标，固定最小间隔更简单、可解释，也足以满足需求。

### 3. 失败后冷却，而不是指数退避重试

任何引擎请求失败（HTTP 错误、超时、解析异常）都记录 `cooldown_until = now + cooldown_seconds`。冷却期内 `acquire(engine)` 返回不可用，`_dispatch` 直接跳过并记录原因。成功请求清除该引擎冷却。

替代方案：对同一引擎重复重试并指数退避。免费接口触发反爬后重试只会加重问题，因此选择快速失败并切换引擎。

### 4. 结果缓存按“引擎 + 查询 + 条数”缓存，返回防御性副本

缓存键为 `(engine, query.strip(), limit)`，值为结果列表的深拷贝与过期时间。命中时不发网络请求；返回前再次拷贝，避免调用方（例如百度链接解析、来源去重）修改缓存对象。TTL 为 0 时禁用缓存。

替代方案：按整次 `search()` 结果缓存。会掩盖引擎顺序与预算行为，且不同 `limit` 无法复用，因此选择引擎粒度。

### 5. 单次调用预算在 `_dispatch` 内计数，缓存命中不计入

`APP_SEARCH_MAX_REQUESTS_PER_CALL` 限制一次 `search()` 实际发出的引擎搜索请求数（不含缓存命中与自定义端点）。达到上限即停止循环：已收集到结果则返回，否则走既有“所有搜索来源均失败”的错误路径。

替代方案：按时间窗口限制全局 QPS。与最小间隔功能重叠，暂不引入。

### 6. 防护开关与参数

新增配置（全部有默认值）：

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| `APP_SEARCH_THROTTLE_ENABLED` | `true` | 总开关；关闭后行为与改造前一致 |
| `APP_SEARCH_MIN_INTERVAL_SECONDS` | `1.0` | 同一引擎两次搜索请求的最小间隔；0 表示不等待 |
| `APP_SEARCH_CACHE_TTL_SECONDS` | `600` | 查询结果缓存有效期；0 表示禁用 |
| `APP_SEARCH_COOLDOWN_SECONDS` | `60` | 引擎失败后的冷却时长；0 表示不冷却 |
| `APP_SEARCH_MAX_REQUESTS_PER_CALL` | `6` | 单次 `search()` 最多发出的引擎请求数 |

百度/搜狗微信的跳转链接解析不在缓存键内，仍属于同一引擎调用的一部分；它受失败冷却保护，但不单独占用最小间隔时间片。该取舍避免一次搜索因解析 8 条链接而额外等待 8 秒，风险由“仅在搜索结果需要解析时发生”限制。

## Risks / Trade-offs

- [最小间隔延长资料阶段耗时] → 默认仅 1 秒且按引擎独立；缓存与预算进一步减少总调用量。需要更快时可把 `APP_SEARCH_MIN_INTERVAL_SECONDS` 调小或设为 0。
- [冷却误伤：一次临时超时导致 60 秒内跳过该引擎] → 仍有其他引擎兜底；冷却时长可配置，设为 0 可关闭。
- [缓存返回过期内容] → 默认 TTL 10 分钟，且只缓存成功结果；调研通常在同一时间窗口内完成。
- [链接解析未单独限流，理论上仍可能高频访问搜狗链接页] → 解析请求数量受结果条数与单次预算约束；后续如需可给解析单独加间隔。
- [进程重启后防护状态清空] → 可接受；重启本身不会造成请求风暴。
- [测试依赖真实时间] → guard 构造时注入 `clock` 与 `sleep`，单测使用假时钟，避免真实等待。

## Migration Plan

- 新增配置均有默认值，无需迁移数据库或调整现有 `.env`。
- 部署后默认启用防护；如出现兼容问题，可设置 `APP_SEARCH_THROTTLE_ENABLED=false` 立即回滚到旧行为。
- 回滚代码时删除 guard 调用即可，缓存与冷却均为内存状态，无持久化残留。
